# B13: a graded evaluation set for the drafted argument

Status: **design, unexecuted.** Written 2026-09-04, for
[#610](https://github.com/prasadtalasila/chitragupta/issues/610)'s B13.

Every measurement this repository holds is about *grounding* -- does the
parse survive, does retrieval surface the right paper, does a claim's
cited source entail it. The paper's Evaluation section says so in its own
preamble, and then says the thing none of it measures: whether the
drafted argument is any good. B13 is the only proposal on #610's list
that would change that, and it is the only one that cannot be run by
writing a script.

This file exists so that the *design* is committed while the execution is
not. Nothing here has been run. No question has been written, no answer
scored, and no number from this method appears in `bench/RESULTS.md` or
anywhere else. Treating a design as a result is the failure mode this
directory's own README warns about, and it would be a worse one here than
usual, because a graded evaluation set is exactly the kind of artefact
that looks authoritative the moment it has numbers attached.

## What is being measured, and what is deliberately not

Retrieval and generation are scored **separately**, both in `[0, 1]` and
reported in percentage points. That split is imported from Xiang et
al. and is the same argument #610's "Alternatives considered" makes
against an end-to-end score: a single number cannot say whether a failure
came from parsing, indexing, retrieval or generation, so a single number
cannot tell you what to fix.

| Side | Metric | What a low value means |
| --- | --- | --- |
| Retrieval | context relevance | The surfaced passages are not about the question |
| Retrieval | evidence recall | The passages that would answer it were not surfaced |
| Generation | faithfulness | The draft asserts things its evidence does not carry |
| Generation | evidence coverage | The draft leaves surfaced, relevant evidence unused |

Questions are calibrated on two axes, again after Xiang et al.:
**knowledge breadth** (how many sources an adequate answer has to draw
on) and **reasoning depth** (how far past restatement it has to go).
A set concentrated in the shallow-narrow corner measures retrieval
wearing a generation costume.

## The confound, stated before the method rather than after it

**Questions generated from a gold chunk favour lexical retrieval.** If a
question is written by reading passage *P* and asking what it answers,
then the terms of the question are *P*'s terms, and BM25 will find *P*
for reasons that have nothing to do with whether BM25 is the right
retriever. This repository has already been bitten by a version of this:
`bench/RESULTS.md`'s third retrieval section exists specifically because
the first two scored against citekeys a human kept *after BM25 surfaced
them*, and it says outright that a paper dense retrieval found which
BM25 never showed has no way to score as a hit.

The consequence for B13 is not a fix, it is a restriction on what may be
claimed: **this set measures change, not route.** It can say a
configuration got better or worse than the same set scored it before. It
cannot be used to choose between retrieval strategies -- that is what the
three ground truths in `bench/RESULTS.md` are for, and two of the three
carry the same caveat in the other direction.

## Why no model writes the questions

The same argument #610 makes against an LLM-as-judge for B9 applies here
one step earlier. The project's position is that a continuous machine
score may inform a decision and may not make it; a set of questions
generated by a model, scored by a model, would be a closed loop whose
agreement with itself is not evidence about the pipeline. Questions are
hand-written by someone who knows the corpus. `docs/TOPIC-DISCOVERY.md`
declines LLM generation for the topic gold set on the same reasoning and
is the precedent.

## What executing this would take

1. **Author the questions.** Stratified over the two axes above, with
   enough per cell to report per-cell rather than only in aggregate.
   Human work, days rather than hours, and the reason this is filed as a
   design.
2. **Record the intended evidence per question** -- which citekeys and
   which passages an adequate answer rests on -- so evidence recall and
   evidence coverage have something to be recalled against. This is the
   half that makes the set reusable: a later version can be scored
   against the same labels.
3. **Commit the set**, anonymised, beside the B9 ratings, so both the
   questions and their labels are re-scorable rather than regenerated.
4. **Write the scorer** as a `bench/` script following this directory's
   `self_check()` convention -- fabricate a difference each of the four
   metrics is supposed to see, and assert it sees it, before any real
   scoring runs.
5. **Score, and report per cell**, with the confound above restated in
   the `bench/RESULTS.md` entry rather than only here.

Steps 1 and 2 gate everything after them, and neither can be delegated to
this pipeline without making the result circular.

## Relationship to B9

B9 (claim-support labelling) is the smaller sibling and is *partly*
executed: `bench/bench_claim_support_labelling.py` builds the stratified,
blinded, order-randomised rating instrument and refuses to compute a
statistic until three humans have filled it in. B13 has no equivalent
partial step -- there is no instrument to build until the questions
exist, because the questions *are* the instrument.
